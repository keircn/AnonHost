roadmap

Here's what's planned for AnonHost. Nothing on this list is guaranteed. Priorities may shift, but this is the direction we're heading. Feel free to email me if you have any suggestions.

up next

Client-Side Encryption

Browser-side encrypt-before-upload so the server stores only ciphertext. The decryption key lives in the URL fragment (#key) and never touches the network. The operator genuinely cannot read your files. We're proudly open source if you wish to audit us!

Burn-After-Reading

Files that self-destruct after the first view. Useful for ephemeral sharing where you don't want a permanent copy lingering on the server. Slightly more secure than setting an expiration date.

planned

Proof-of-Work Rate Limiting

Replace the basic IP rate limiter with a hashcash-style proof-of-work challenge. No IP addresses kept anywhere in the system, even ephemerally.

Metadata Scrubbing

Strip EXIF, GPS coordinates, author info, and other metadata from images and documents before storage. What you share is what stays.

considering

Content Integrity Hashes

Serve SHA-256 hashes alongside files so recipients can verify nothing was tampered with server-side.

File Size Obfuscation

Round or hide exact file sizes from the API to reduce metadata leakage. Still thinking about how necessary this is.

View-Based Expiry

Delete files after N views or the first download, giving more granular control over file lifetimes.

Database Encryption at Rest

Encrypt the SQLite database so filenames, deletion tokens, and archive metadata aren't readable if the volume is compromised.
